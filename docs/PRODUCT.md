# 产品设计

本文描述**目标体验与范围**，不等同于当前仓库已实现功能；实现状态见仓库根目录 [README](../README.md) 与 [路线图](ROADMAP.md)。

---

## 产品定位

**Minecraft Utilities** 面向 Minecraft 玩家，提供多款**本机、本地优先**的实用能力（桌面端 Tauri + Python 引擎）。路线图以**少折腾、可预览、可回退**为共同原则横向扩展。

**当前主线能力（首期深入）**：在常见启动器、**.minecraft/versions/** 版本隔离前提下，围绕 **CurseForge zip** / **Modrinth mrpack** 将实例中的**模组与清单**与作者发布包对齐（含 `overrides` 与清单差异）；强调 **dry-run 与备份**。

---

## 要解决什么问题

在**常见 Minecraft 启动器**生成的整合包实例中，玩家希望在不折腾存档与自定义配置的前提下，把**模组列表**对齐到作者发布的**新版本**整合包（并尽量安全地处理 `overrides` 与清单）。上述场景是 **Minecraft Utilities** 的首个落地重点，而非产品边界上限。

---

## 用户与场景

- **主要用户**：希望「少步骤、少术语」的 Minecraft 玩家；首期深度场景为**整合包 / 清单对齐**需求者。
- **实例与路径**：以用户本机的 **整合包实例根目录** 及其中 **`.minecraft`** 布局为准；具体相对路径（如 `mods/`、`saves/`）随启动器与版本隔离设置而异，实现阶段需**实机对照**并写入文档与向导。
- **前提（第一期）**：用户**已经安装**整合包的某一版本，本机存在 **`.minecraft` 实例目录**。
  - **纳入**：Minecraft **版本隔离**落在 **`.minecraft/versions/`** 下的布局（每个游戏版本对应 `versions/<版本或配置名>/` 等资源根，具体命名以实测为准）。
  - **暂不纳入**：**未隔离**（根 `.minecraft` 下直接共用 `saves` / `config` 等、无 `versions` 分版本目录）的路径；后续单独立项再支持。
- **输入**：
  - **CurseForge** 官方整合包 **`*.zip`**（内含 `manifest.json`）。
  - **Modrinth** 官方整合包 **`*.mrpack`**（内含 `modrinth.index.json`）。
- **目标版本（第一期）**：由用户再提供一份**新**的 zip/mrpack（或等价解压目录）作为「目标清单」来源（部分升级路径依赖此文件，见下节）。
- **待定**：自动从 CurseForge / Modrinth 拉取**最新 Release**，免用户自备第二份包（需单独立项：项目标识、版本通道、合规与限流）。

### 升级路径（仅 `versions` 隔离场景）

工具定位为**升级**：在已有实例上对齐模组与版本，而非从零教用户安装 Minecraft。

| 路径                   | 用户现状                                                                              | 工具目标                                                                                                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. 双版本并存**      | `.minecraft/versions/` 下**已存在旧版与新版**两个版本目录（例如已导入新整合但未迁档） | 将**旧版**中的**存档（如 `saves`）**与**配置等资源**按规则**迁移到新版**对应目录；可选再对新版执行模组 plan/apply 与清单对齐（与既有「目标 zip/mrpack」流程衔接处实现阶段定稿）。 |
| **B. 单版本 + 压缩包** | `versions/` 下**仅有一个**已安装版本；手中有一份**整合包压缩包**（zip/mrpack）        | 先执行**新包安装流程**（解压/安装至 `versions` 或由启动器生成等价目录结构），再将**存档、config、资源包等**从旧版迁移至**新装版本**；随后再模组 diff/下载/写回。                  |

**说明**：上表中的「旧版 / 新版」目录名、是否与启动器的「版本隔离」设置一一对应，须在 **`versions-layout-docs-qa`** 中通过**实测**后写入实现与向导文案；迁移须支持 **dry-run 与可撤销备份** 策略（与全局风险章节一致）。

## 懒人包 / 开箱体验（目标）

| 目标                 | 说明                                                                                            |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| **开箱即用**         | Windows 优先：安装包或绿色解压目录；双击进入图形向导（Tauri 2 + Vue 3）。                       |
| **无需额外安装依赖** | 终端用户不必单独安装 Python、Node.js 或配置 PATH；运行时依赖随安装包分发。                      |
| **尽量不折腾系统**   | 不要求改环境变量、hosts 等；**CurseForge API Key** 仅在应用内粘贴一次，保存到用户应用数据目录。 |
| **纯新手友好**       | 向导步骤少；默认 **dry-run** 再执行；错误信息可读且可一键复制。                                 |

模组文件仍需**联网下载**。「零配置」指**不必安装开发/运行时栈**，不承诺完全离线。

## 推荐工作流

1. 在所用启动器中打开要升级的整合包实例，确认**实例根目录**（及 `.minecraft/versions/` 等布局，见上文）。
2. 准备**目标版本**的官方 **`.zip` 或 `.mrpack`**（第一期用于生成变更计划）。
3. 在本工具中选择目标包与实例目录，先查看 **plan**，确认后再 **apply**。
4. 若为 **CurseForge** 包，按提示在应用内配置 [CurseForge API Key](https://docs.curseforge.com/rest-api/#authentication)；Modrinth 包通常无需 Key。

**合规**：用户须自行确保有权下载与使用相关模组，并遵守 CurseForge、Modrinth 与模组作者的条款。

---

## 风险与边界（产品侧）

- **存档**：设计原则是**默认不整盘覆盖**世界与玩家配置；仍强烈建议升级前**完整备份**实例目录。
- **Windows SmartScreen**：未签名 exe 可能被拦截；发行方可考虑代码签名证书。
- **路径差异**：不同启动器生成的 `.minecraft` 子结构可能不同；文档与向导须以**实测**为准，避免硬编码单一启动器专有路径。
